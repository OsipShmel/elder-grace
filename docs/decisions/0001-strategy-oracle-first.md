# 0001 — Стратегия: сначала эталон, режим C как площадка, ядро из реальных портов

- Статус: принято
- Дата: 2026-11-07

## Контекст

Первоначальный план предполагал один путь: свой движок под Elden Ring поверх данных игры (режим A), без Wine/CrossOver в какой-либо роли. Пользователь хочет:
- в обозримом будущем видеть результаты (переработанные шейдеры, рост FPS), а не только через годы паритета;
- инструмент, пригодный для портирования разных игр, а не одной.

Ограничения:
- macOS не смешивает arm64 и x86_64 в одном процессе. Пока работает оригинальный exe, всё в его процессе идёт через Rosetta.
- Опыта подобных портов у команды нет, поэтому риск утонуть в проектировании обобщённого движка высокий.

## Решение

1. **Сначала эталон.** Оригинальная игра под CrossOver/GPTK — постоянный измерительный прибор: базовая линия, frame capture, дифференциальные сравнения. Как способ запуска нашего продукта трансляция не используется.
2. **Режим C как учебная площадка.** Shim внутри Wine: наблюдение (C0) → подмена шейдеров (C1) → при необходимости вынос рендера в отдельный нативный процесс (C2). Он быстро даёт цифры и строит инструменты, которые нужны и режиму A.
3. **Режим A как долгосрочный путь** с теми же крейтами ядра.
4. **Развилки по цифрам** после фаз 1, 3 и 5 (см. `PLAN.md`): CPU-bound или GPU-bound, где потолок C.
5. **Ядро обобщаем по второй точке использования**, а не заранее. Игровая специфика — в отдельном репозитории игры `grace-<игра>` (см. ADR 0003).
6. **Режим B** (статическая рекомпиляция exe) вне рамок проекта.

## Последствия

- Wine/GPTK/CrossOver нужны в окружении разработки (как эталон), но не распространяются и не являются частью продукта.
- Нужен shim под Windows x86_64 — отсюда требование кросс-компиляции (см. 0002).
- Первые вехи пользователя — это игра с shim и подменой шейдеров, а не только «прогулка призраком».
- Если на развилке 1 игра окажется CPU-bound, режим C сворачивается до инструментов, и главной становится ставка на A.
